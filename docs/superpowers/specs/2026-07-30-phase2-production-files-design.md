# Phase 2 Complete Production Files Design

## Status

- Date: 2026-07-30
- Design status: approved by the user
- Roadmap position: phase 2 of the approved Shopify 3D app roadmap
- First release target: local browser generation and download

## Goal

Upgrade the existing **Save design** action so every supported jersey design produces one complete local production ZIP. The package must contain the editable design state, a 4096 x 4096 UV atlas with every printable layer, deterministic front and back previews, a Chinese UV reference PDF, and an integrity manifest.

This phase produces a reliable reference and data-exchange package. It does not upload files, associate a paid order, or claim that the PDF is a factory 1:1 cutting pattern.

## Scope

### Included

- Complete 4096 x 4096 UV atlas generation.
- Base template and zone colors.
- Player names and numbers.
- Custom text.
- Preset artwork and customer-uploaded artwork.
- Legacy bottom pattern data when an opened design already has it enabled.
- Fixed front and back preview PNGs.
- Two-page Chinese UV reference PDF.
- SHA-256 manifest and production ZIP.
- One-click generation through the existing **Save design** action.
- Chelsea and FN8788 model verification.

### Excluded

- R2, D1, cloud upload, signed downloads, or cleanup jobs.
- Shopify paid-order association or `orders/paid` webhooks.
- Shopify Admin Block or custom-order list.
- GLB upload or model administration.
- Native CDR generation.
- Factory 1:1 cutting dimensions, bleed, seam allowance, grading, or piece numbers.
- Changes to product pricing, checkout, inventory, or the live Shopify theme.

## User flow

1. The shopper finishes editing the jersey.
2. The shopper clicks **Save design**.
3. The app freezes an immutable snapshot of the current design.
4. The app prepares all six package files locally.
5. The app verifies the manifest against the generated bytes.
6. The app exposes one **Download production ZIP** link.
7. If the design changes, the previous prepared download becomes stale and is revoked.

The ZIP contains the editable `design.json`, so no second save button is added. **Open design** continues to accept a JSON file extracted from the ZIP.

## Package contract

The local phase-2 package is named:

```text
<product-id>-design-<8-character-design-fingerprint>.zip
```

It contains exactly:

```text
design.json
uv-atlas.png
uv-reference.pdf
preview-front.png
preview-back.png
manifest.json
```

Phase 2 has no Shopify order number. Phase 3 may wrap the same verified artifacts in an order-numbered filename after payment without changing the six-file contract.

### Design fingerprint

The design fingerprint is the first eight lowercase hexadecimal characters of SHA-256 over a canonical value containing:

- production package schema version;
- product ID and selected variant/size;
- model ID and immutable model version;
- normalized configurable state;
- UV export version.

Object keys are sorted recursively before hashing. Volatile timestamps and generated filenames are excluded, so an unchanged design keeps the same fingerprint even when exported again.

## Model production metadata

Each product model definition must expose:

```text
id
version
uvExportVersion
uvAtlasSize
```

The first version uses `uvAtlasSize = 4096`. Model metadata is explicit configuration, not inferred from a mutable URL at export time. Later model-management work may create these values automatically, but old orders and packages must continue referencing the immutable version used to generate them.

## Complete UV atlas

### Base layer

The baker starts from the existing garment appearance UV canvas so template and zone colors match the live preview. If a legacy opened design has an enabled continuous bottom pattern, its latest valid baked atlas is composed using the same projection metadata already used by the preview.

New designs keep the hidden bottom pattern disabled and do not create an invisible pattern layer.

### Personalization and artwork layers

The live renderer already owns the final exterior-only decal geometries for player sets, custom text, preset artwork, and uploaded artwork. The production baker reuses those validated surfaces instead of independently reconstructing placement from UI fields.

For each printable decal triangle:

1. Read the triangle's decal texture UV coordinates.
2. Project each exterior decal vertex inward to the underlying printable garment mesh.
3. Read the garment intersection UV through barycentric interpolation.
4. Affine-map the decal texture triangle onto the matching garment UV triangle.
5. Composite triangles in the same render order as the live scene.

The shared exterior-facing triangle filters and garment mesh allowlist remain authoritative. A triangle without a valid underlying garment UV is not silently skipped. The package fails with a clear error unless the mapped coverage meets the strict expected coverage for that layer.

The baker handles UV seam crossings explicitly and preserves transparent decal pixels. It does not rasterize DOM selection controls or editor toolbars.

### Color and image rules

- Output MIME type: `image/png`.
- Atlas size: product model configuration, initially 4096 x 4096.
- Color space metadata: sRGB reference output.
- Transparent pixels remain transparent outside printable UV islands.
- Uploaded images use the exact decoded source already accepted by the editor.
- The generated Atlas is the exact pixel artifact; the PDF is only a scaled visual reference.

## Front and back previews

The renderer exposes a production-capture operation that:

1. waits for the model, appearance textures, personalization decals, and artwork decals to be ready;
2. saves the current camera, orbit target, selection, and interaction state;
3. hides transient selection effects;
4. renders fixed front and back camera presets against a neutral background;
5. exports two PNG blobs at a stable configured size;
6. restores the shopper's previous view and interaction state in a `finally` path.

Preview capture must not animate the visible camera or leave the editor on a different side after export.

## Chinese UV reference PDF

The PDF contains two A4 landscape pages.

### Page 1: design reference

- Title: `球衣定制生产参考`
- Status: `本地设计，尚未关联 Shopify 订单`
- Product and selected size.
- Model ID, model version, UV export version.
- Design fingerprint.
- Generation time.
- Atlas resolution and sRGB reference.
- Selected template and zone colors, including hexadecimal color values.
- Front and back preview images with clear Chinese labels.
- Warning: `此文件为 UV 参考资料，不是工厂 1:1 裁片文件。`

### Page 2: UV reference

- Full UV atlas scaled to the printable page area without cropping.
- Atlas pixel dimensions.
- Design fingerprint and page number.
- Warning repeated at the bottom.

Chinese labels are first rendered into a page canvas and then embedded as raster page images in a minimal PDF container. This avoids missing or corrupted Chinese glyphs on computers without an embedded CJK PDF font. The separately supplied PNG remains the lossless production-data reference.

## Manifest

`manifest.json` contains:

```text
schemaVersion
designFingerprint
productId
variantId
size
model.id
model.version
uvExportVersion
atlas.width
atlas.height
atlas.colorSpace
generatedAt
files[]
```

Each `files[]` record contains:

```text
name
mediaType
byteLength
sha256
```

The manifest lists the other five files and does not recursively hash itself. All hashes use lowercase hexadecimal SHA-256 without a `sha256:` prefix inside the manifest.

Before exposing the ZIP download, the app re-reads the five prepared blobs, verifies their names, byte lengths, and SHA-256 values against the manifest, then packages those exact bytes plus `manifest.json`. Any mismatch prevents download.

## Module boundaries

New responsibilities stay out of `ConfiguratorPage.jsx` and `garmentRenderer.js`:

- `scene/productionAtlasBaker.js`: map validated live decal surfaces into garment UV space and produce the complete PNG atlas.
- `scene/productionPreviewCapture.js`: fixed-view capture helpers and state restoration.
- `designs/productionFingerprint.js`: canonicalization and stable design fingerprint.
- `designs/productionReferencePdf.js`: two-page Chinese raster reference PDF.
- `designs/productionManifest.js`: hash, manifest creation, and artifact verification.
- `designs/productionPackage.js`: orchestration of design JSON, renderer artifacts, PDF, manifest, and ZIP.

Existing modules are extended narrowly:

- `productionBundle.js`: accept the six-file package instead of only JSON and Atlas while retaining the small internal ZIP writer.
- `GarmentRenderer`: expose a read-only production artifact provider and wait for renderer readiness.
- `ProductStage`: register and unregister the provider with the page.
- `ConfiguratorPage`: coordinate the immutable save request and prepared download state.
- `productDefinitions.js`: add immutable model production metadata.

No new runtime dependency is required.

## Concurrency and lifecycle

- Each save request has a monotonically increasing token.
- Only the latest request may publish a download.
- State changes invalidate the currently prepared package.
- Unmounting cancels publication and revokes temporary object URLs.
- Renderer capture and atlas baking use the frozen state/model version from the same request.
- Canvases and temporary blobs are created sequentially where practical and released after their bytes enter the final ZIP.
- The save button remains disabled while renderer mutations or package generation are pending.

## Errors

The app reports a clear Chinese failure and does not expose a ZIP when:

- the renderer or model is not ready;
- a printable mesh has no UV;
- a decal cannot map back to the garment UV;
- an image fails to decode or taints Canvas;
- PNG or PDF encoding is unavailable;
- browser SHA-256 is unavailable;
- a generated file is empty;
- manifest verification fails;
- ZIP creation fails;
- the design changes before generation completes.

The current design remains editable after failure. No default image, default model, empty file, or stale package is presented as success.

## Verification

### Automated

- Stable canonical fingerprint and filename.
- Base template and zone colors appear in the Atlas.
- Front/back player sets, custom text, preset artwork, and uploaded artwork map to the correct UV islands.
- Front layers do not appear on back islands and vice versa.
- Transparent decal pixels and layer order are preserved.
- Legacy enabled bottom patterns remain compatible.
- Atlas is a 4096 x 4096 PNG in the production integration path.
- Preview capture restores camera, selection, controls, and render state on success and failure.
- PDF has two A4 landscape pages and contains both preview images and the Atlas reference page.
- Manifest byte lengths and SHA-256 values match actual artifacts.
- ZIP contains exactly the six required filenames.
- Missing, empty, renamed, or altered artifacts fail verification.
- Save/open/export round-trip keeps the same normalized design and fingerprint.
- Stale and concurrent save requests cannot publish an obsolete package.

Unit tests use smaller canvases where pixel dimensions are not the subject under test. At least one integration test asserts the configured 4096 output contract.

### Real-model and browser acceptance

For both Chelsea and FN8788:

1. Add front and back player sets, custom text, preset artwork, and uploaded artwork.
2. Export and download the ZIP.
3. Extract all six files.
4. Compare front/back previews with the live 3D design.
5. Inspect the 4096 Atlas for correct side placement and complete layers.
6. Render both PDF pages to PNG and visually check Chinese text, spacing, image sharpness, and lack of cropping.
7. Verify each manifest hash against the extracted file.
8. Reopen `design.json`, export again, and compare normalized state and fingerprint.

The full Vitest suite and both app and Shopify production builds must pass.

## Rollback

- Keep the existing JSON-only save path behind the phase-2 integration commit boundary.
- Reverting the phase-2 commits restores the previous **Save design** behavior.
- No cloud objects, database rows, orders, products, prices, or live-theme assets require cleanup.
- Existing phase-1 production deployment remains the immediate Worker rollback target until phase 2 is separately approved for release.

## Phase boundary

Completion of this phase means the browser can create and validate a complete local production-reference package. It does not mean factory-ready 1:1 output or automatic Shopify order fulfillment.

Phase 3 begins only after separate approval and adds R2/D1 storage, pre-cart upload, paid-order association, retention, and cloud failure recovery around this unchanged package contract.
